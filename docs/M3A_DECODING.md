# M3a — CDR decoding and typed signal access

Scope: MCAP recordings whose messages are ROS 2 CDR with an embedded `ros2msg` schema (rosbag2 MCAP storage, or a bare `.mcap`).
Out of scope (not implemented): event-response correlation (M3b), anomaly detectors (M3c), localization (M3d), reporting (M3e),
image / point-cloud analysis, incident memory, retrieval, LLMs. The Collector still never decodes payloads.

## What was added (all additive)

| Piece | Where |
|---|---|
| Isolated decoder adapter, schema field-type index, signal grammar, float semantics | `investigator/cdr.py` (new; the **only** importer of the third-party decoder, enforced by a test) |
| Observation / evidence hooks (typed leaves, per-topic codec, blind-spot qualities) | `investigator/observations.py`, `investigator/engine.py` |
| `evidence decode PATH -t TOPIC [-n N] [--json]` (inspect what a topic decodes to) | `investigator/decoding.py`, `cli.py` |
| Optional extras | `pyproject.toml`: `ros2`, `xcheck` |
| Synthetic example | `examples/m3a/` (generated by `python -m tests.make_cdr_example examples/m3a`) |
| Tests / benchmark | `tests/test_cdr_m3a.py`, `tests/cdr_fixtures.py`, `scripts/bench_cdr.py` |

Contract schema stays `1.0`; Phase 2 JSON output is byte-identical (new fields are omitted when absent).

## Signal paths

Dotted keys. An all-digit step indexes a list (`position.0`). `field[key=value]` selects the element of array `field` at the index where the sibling
array `key` holds `value`: `position[name=elbow]` on `JointState`. Values may contain letters, digits, `_ - / :` (not `.`, which separates steps).
Zero or several matches are blind spots (`signal_missing`, `signal_ambiguous`), never a guess. Works for JSON messages too.

Values: integers exact; float64 by shortest round-trip text; float32 by the shortest decimal that reads back as that float32 (so `0.1` is `0.1`, and
a limit written `12.3` behaves as written); NaN/Inf → quality `non_finite` with no value; bool and string unchanged. Each observation carries `ros_type`.

Provenance is unchanged from Phase 2: artifact digest, message index (position in the file), topic, MCAP log time, clock domain `mcap_log_time`.
Payload `header.stamp` is not used as a clock in M3a (deferred to M3b so clock domains stay distinct).

## Failure statuses (nothing is fabricated, nothing raises)

Topic level (investigation → `insufficient_evidence`): `payload_decoder_unavailable` (extra not installed; message says `pip install physicore-collector[ros2]`),
`payload_schema_missing`, `payload_schema_invalid`, `payload_encoding_not_supported` (schema encoding other than `ros2msg`, e.g. `ros2idl`; message encoding other than `cdr`),
`payload_type_out_of_scope` (Image, PointCloud2, …; decoder never invoked).
Per message (blind spots): `payload_malformed` (truncated / corrupt, including every proper truncation), `payload_unsupported_type` (e.g. `wstring`),
`payload_undecodable` (e.g. over the 8 MiB per-message cap). Counts per topic are in `evidence.payload_decoding`.
A broad `except Exception` is used only at the third-party decoder call, so a decoder bug becomes a status rather than a crash.

## Dependency and licensing report

| Package | Role | Version tested | License evidence |
|---|---|---|---|
| `mcap-ros2-support` | decoder (extra `ros2`) | 0.6.0 | PyPI classifier MIT; upstream repository root `LICENSE` is MIT (Foxglove). **Gap:** the package metadata has no license field and neither wheel nor sdist ships a LICENSE file. Vendors a rosidl message parser (Apache-2.0). |
| `mcap` | reader (already a dependency) | 1.6.0 | MIT |
| `lz4`, `zstandard` | via `mcap` | 4.4.5, 0.25.0 | BSD |
| `rosbags` | **tests only** (extra `xcheck`): independent serializer and cross-check decoder | 0.11.9 | Apache-2.0 (`numpy`, `ruamel.yaml`, `apsw`, `lz4`, `backports.zstd` transitively) |

Assessment: licensing is clear enough to adopt as an *optional* extra (MIT classifier + MIT upstream repo), but the missing in-package license file is a gap
worth a human check before redistributing a bundle that contains it; nothing is vendored into this repository, so the default install is unaffected.
Maintenance: releases 0.5.7 (2025-12-24) and 0.6.0 (2026-10-19), recent upstream commits. Limits: `ros2msg` only (no `ros2idl`), no `wstring`.
The adapter is the single seam, so replacing the decoder touches one module.

## Known limitations

- No real robot / rosbag2 recording was available: everything is synthetic (rosbags serializer + `mcap` writer). Real-recording compatibility, `ros2idl`
  schemas (Humble+ custom types sometimes use them), and the ROS 2 integration tests (skipped here, no ROS 2 install) remain unverified.
- Trailing bytes after a valid message are accepted silently by the decoder (truncation is never silent).
- Views cap long arrays at 16 leaves; signals can still address any element.
- Decoding is per message in Python: see the measured throughput in the report; large messages (covariance-heavy Odometry) are ~4x slower than scalars.
- Constants declared in a message definition are not exposed as values.

## Recommendation for the next milestone

M3b (event-response correlation) is the natural next step: it needs only typed signals plus the payload-stamp clock domain. Before it, run M3a on one or two
real rosbag2 MCAP recordings (including one using `ros2idl` if your stack produces them) to find out whether `ros2idl` support is needed.

## Measured decoding cost (synthetic, this machine)

`python -m scripts.bench_cdr --messages 20000`; Python 3.13.17, x86_64, mcap-ros2-support 0.6.0; whole Investigator run (read + decode + one signal + check), fresh process per case.
Process baseline after imports: 37 MB.

| Messages (20,000 each) | File | Time | Throughput | Peak RSS |
|---|---|---|---|---|
| `std_msgs/Float64` | 1.2 MB | 0.28 s | ~73k msg/s | 61 MB |
| `JointState`, 7 joints | 6.9 MB | 0.67 s | ~30k msg/s | 103 MB |
| `Odometry` (2x36 covariance) | 15.4 MB | 1.40 s | ~14k msg/s | 170 MB |

Memory grows with the number of messages held for the investigated signals (about 1–7 KB per message here), so very long recordings with large messages are
not bounded by a streaming design yet; the existing evidence budget caps what is retained but this was not stress-tested beyond these sizes.
An earlier scratch run (50k JointState in ~0.96 s) is consistent with the JointState row. Do not extrapolate to real recordings.
